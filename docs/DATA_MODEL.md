# Data model

Full model definitions: `apps/web/prisma/schema.prisma`. This document is
the narrative — why the shapes are what they are.

## Tenancy root

Every tenant-scoped table carries `institutionId`. `Institution.type` is
`SCHOOL` or `COLLEGE`; `Institution.settings` (JSON) carries
`academicUnitLabels` and `confidenceThresholds` — institution-specific
configuration that would otherwise force a schema fork.

## The school/college abstraction

Three tables model both institution types with no forked schema:

- **`AcademicUnit`** — a self-referential tree via `parentId`, discriminated
  by `kind`. A school builds `GRADE -> SECTION`; a college builds
  `DEPARTMENT -> SEMESTER -> COURSE`. `metadata` (JSON) holds kind-specific
  extras (e.g. `gradeLevel`, `semesterNumber`) without new columns.
- **`Cohort`** — the atomic, enrollable, attendance-taking group. It attaches
  to whichever `AcademicUnit` sits at the bottom of that institution's tree
  (a `Section` for a school, a `Course` for a college).
- **`Enrollment`** — links a `Student` to a `Cohort`, with a status so a
  transfer/withdrawal doesn't delete history.

Worked example — a school:

```
AcademicUnit(kind=GRADE, name="Grade 8")
  └─ AcademicUnit(kind=SECTION, name="Section A", parentId=<grade 8>)
       └─ Cohort(name="Grade 8 - Section A", academicUnitId=<section A>)
```

Worked example — a college:

```
AcademicUnit(kind=DEPARTMENT, name="Computer Science")
  └─ AcademicUnit(kind=SEMESTER, name="Semester 3", parentId=<CS dept>)
       └─ AcademicUnit(kind=COURSE, name="CS301", parentId=<semester 3>)
            └─ Cohort(name="CS301 Fall 2026", academicUnitId=<CS301>)
```

Both examples produce identically-shaped rows in the same three tables;
only `kind` values and tree depth differ.

## Attendance capture

- **`AttendanceSession`** — one roll call. `status` follows the state
  machine in `modules/sessions/service.ts#canTransitionSessionStatus`:
  `OPEN -> CAPTURING -> PROCESSING -> REVIEW -> FINALIZED`, cancellable from
  any non-terminal state.
- **`SessionImage`** — 1–3 classroom photos per session (`sequenceNumber`
  1/2/3), each with an optional `qualityScore` from the quality-check step.
- **`FaceEmbedding`** — one row per enrolled student's reference face
  vector. `embedding` is `Unsupported("vector(128)")` (see below).
  `modelName`/`modelVersion` record which backend produced it, so a future
  model swap can identify and re-embed stale rows.

## AI-advisory / faculty-authoritative attendance records

`AttendanceRecord` is unique per `(sessionId, studentId)` and carries:

- `aiResult` / `aiConfidence` — written once by the recognition pipeline via
  `modules/recognition-results/service.ts#classifyRecognitionConfidence`.
  Never edited afterward.
- `finalResult` / `isManuallyCorrected` — the authoritative result. Only
  `modules/attendance/service.ts#correctAttendanceRecord` may change
  `finalResult`, and it always does so inside a transaction that also
  inserts an `AttendanceCorrection` row.

`AttendanceCorrection` is append-only: `previousResult`, `newResult`,
`changedByUserId`, `reason` (optional), `source` (`FACULTY_REVIEW |
ROLL_CALL | ADMIN_OVERRIDE | PUBLIC_API`), `changedAt`. Rows are inserted,
never updated or deleted — this is the audit trail the product spec
requires ("original AI result, final result, who changed it, when, optional
reason").

## pgvector

Prisma has no native vector scalar type, so `FaceEmbedding.embedding` is
declared as `Unsupported("vector(128)")`. Consequences:

- `prisma generate` produces no typed field for it — reads/writes go through
  `prisma.$queryRaw` / `$executeRaw`.
- `CREATE EXTENSION vector` is not generated by Prisma. It is hand-written as
  the first statement of `migrations/20260917000000_init/migration.sql`, and
  must be carried forward by hand if that baseline is ever rebuilt.
- **There is no ANN index, and `<=>` is not used.** Candidate templates are
  loaded for the session's cohort (or its `CohortSubject`, for an elective) and
  ranked in process, so every score in a run comes from one cosine
  implementation shared with `services/face-ai`. See
  `modules/recognition-results/repository.ts` and docs/BENCHMARKS.md §4. An
  HNSW index with no reader would be write-side cost only.
- The scope filter is the point, and it is not a performance measure. A pool of
  50–100 templates is small enough that an exact scan wins outright; the reason
  the cohort join is mandatory in every loader signature is that matching a face
  against another class's templates is a correctness bug.
- **If ANN is ever adopted**, HNSW over IVFFlat: HNSW needs no `lists` tuning
  ahead of time and keeps good recall as data grows, whereas IVFFlat's recall
  depends on choosing `lists` relative to row count up front — a poor fit for an
  incrementally-growing, per-institution table. docs/DATABASE_OPERATIONS.md §5
  carries the exact statement.

## Indexes

Every index is declared in `schema.prisma` with the read it exists for written
next to it, and created by one of the two migrations. The set is deliberately
small: indexes were added for named query patterns, not for every foreign key.
Two consequences worth knowing before adding more:

- A composite that leads with column `a` also serves lookups on `a` alone, so
  `Student` needs no `@@index([institutionId])` — `@@unique([institutionId,
  studentCode])` already covers institution-scoped listing.
- PostgreSQL does not index foreign keys automatically. Most FK columns here are
  `ON DELETE RESTRICT` and the referenced rows are never deleted, so the missing
  index costs nothing. `AttendanceRecord.matchedEmbeddingId` is the exception —
  it is `ON DELETE SET NULL` and the retention purge deletes templates in
  batches — so it is indexed.

Operational procedures — applying, rolling back, backup, restore — are in
docs/DATABASE_OPERATIONS.md.

## Integration layer

- **`ApiKey`** — `hashedKey` (HMAC-SHA256 of the raw key, never stored in
  plaintext), `scopes`, `revokedAt`. See `modules/integrations/api-key-auth.ts`.
- **`WebhookEndpoint`** — registered per institution; delivery is deferred.
- **`AuditLog`** — generic `(entityType, entityId, beforeJson, afterJson)`
  trail for integration/admin actions, distinct from `AttendanceCorrection`
  which is attendance-specific and always faculty/system-actor-scoped.
